# File Storage — Pune Caring Hands

## Uploaded File Types

| File Type                | Purpose                                | Max Size |
| ------------------------ | -------------------------------------- | -------- |
| Payment screenshot       | Proof of UPI payment                   | 5MB      |
| Medicine prescription    | Required for medicine delivery service | 5MB      |
| Medical reports (future) | Lab/X-ray results                      | 10MB     |

---

## Storage Approach

**Use secure object storage — NOT PostgreSQL for binary files.**

The database stores only the file reference (object key), not the binary content.

```
Database: Payment.proofFileKey = "payments/2024/03/PCH-20240315-0042-proof.jpg"
Storage:  Actual file in object storage bucket
```

---

## Storage Provider

The exact provider is selected during implementation.
Recommended options:

- AWS S3 (or compatible: Cloudflare R2, MinIO for local dev)
- Google Cloud Storage
- Azure Blob Storage

Configure via environment variables — do NOT hardcode provider details.

```env
STORAGE_PROVIDER=s3
STORAGE_ENDPOINT=https://s3.ap-south-1.amazonaws.com
STORAGE_ACCESS_KEY=<access_key>
STORAGE_SECRET_KEY=<secret_key>
STORAGE_BUCKET=pune-caring-hands
STORAGE_REGION=ap-south-1
```

For local development, use MinIO or local filesystem with the same interface.

---

## File Access Control

- Storage bucket must be **private** — no public access
- Files are accessed via **time-limited signed URLs** generated by the backend
- Signed URLs expire after a short duration (e.g. 15 minutes)
- Frontend never receives a permanent storage URL

### Admin Access Flow

```
Admin requests to view payment proof
        ↓
Backend generates signed URL (15 min expiry)
        ↓
Backend returns signed URL to admin frontend
        ↓
Admin frontend displays image via signed URL
        ↓
URL expires — file no longer accessible via that URL
```

---

## File Naming Convention

Use a structured, collision-resistant key format:

```
{category}/{year}/{month}/{bookingRef}-{purpose}.{ext}

Examples:
  payments/2024/03/PCH-20240315-0042-proof.jpg
  prescriptions/2024/03/PCH-20240315-0043-prescription.pdf
```

---

## Upload Endpoint

```
POST /api/v1/bookings/:id/payment/proof
Content-Type: multipart/form-data
```

Backend responsibilities:

1. Validate JWT (if admin upload) or booking ownership (if patient upload)
2. Validate file type (JPEG, PNG, PDF only)
3. Validate file size (max 5MB)
4. Generate storage key
5. Upload to object storage
6. Store key in database
7. Return success response (NOT the storage URL)

## Local Development

For local development without a cloud storage account:

- Use MinIO (S3-compatible, runs locally via Docker)
- Or use local filesystem storage with a simple abstraction layer

```yaml
# docker-compose.yml (local dev only)
minio:
  image: minio/minio
  ports:
    - '9000:9000'
    - '9001:9001'
  environment:
    MINIO_ROOT_USER: minioadmin
    MINIO_ROOT_PASSWORD: minioadmin
  command: server /data --console-address ":9001"
```

---

## What NOT to Do

- Do NOT store binary files in PostgreSQL
- Do NOT make the storage bucket publicly accessible
- Do NOT return permanent storage URLs to the frontend
- Do NOT hardcode storage credentials
- Do NOT skip file type and size validation
- Do NOT use user-provided filenames — generate server-side keys
